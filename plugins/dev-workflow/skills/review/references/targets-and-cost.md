# Targets, large diffs and cost

## Targets

- **Pull request**: `gh pr diff <n>` shows the PR as GitHub sees it. The PR's base is in
  `gh pr view <n> --json baseRefName`. A reviewer that needs the code around a line reads the local checkout, so
  when the PR's branch is not checked out, the context it reads may be older than the PR. Say so in "Not
  covered".
- **This branch**: use three dots (`base...HEAD`). That shows what the branch added since it left the base, not
  what `main` gained since.
- **Uncommitted**: `git diff HEAD` covers staged and unstaged changes. Untracked files are not in any diff. List
  them with `git status --porcelain` and give the paths to the reviewers.

## Large diffs

Reviewers read every changed line. Past about 2,000 lines:

1. Skip generated and vendored files: lock files, `dist/`, `build/`, snapshots, migrations generated by a tool.
   Name them in "Not covered".
2. Offer to split by top-level folder, with one review per folder.
3. Never sample silently. A review that skipped files says which ones.

## Cost

One review starts four subagents. The three specialists use `sonnet`. The adversarial reviewer uses the session's
model (`inherit`), because refuting needs the strongest reasoning available. Each subagent reads the diff and
the code around it in its own context, so a big diff costs about four times its size in input tokens. For a
one-line change, a single reviewer is enough: offer it.

## Why an adversarial pass

Reviewers that are asked to find problems will find some, real or not. Sorting them costs the reader more than
the review saved. The adversarial reviewer reads the code with the opposite goal: to prove each finding wrong.
Only what survives reaches the user. It also makes one fresh attack, because three specialists can share a blind
spot.
